# Public API Discovery

`public-apis/public-apis` — это discovery layer, а не источник данных и не гарантия актуальности.

Цель: `запрос → какие данные нужны → кандидаты в каталоге → проверка официального источника → сравнение → конкретный способ получить данные`.

Не пересказывай репозиторий. Не выдумывай API. Не ставь числовой рейтинг.

В каждом ответе разделяй три слоя и помечай их явно:

- **Каталог** — строка в `public-apis/public-apis`
- **Официальная документация** — сайт или docs владельца API
- **Вывод** — сопоставление с требованиями пользователя

Если каталог и официальная документация расходятся, доверяй документации и явно укажи расхождение. Если официальный сайт показывает, что API deprecated, недоступен или сменил условия, сообщи об этом и не рекомендуй старую строку каталога.

## Когда использовать

Используй skill, когда задача требует:

- найти внешний источник структурированных данных;
- получить данные через API;
- найти бесплатный или условно бесплатный API;
- найти API для конкретной категории данных;
- заменить ручной web scraping API-интерфейсом;
- подобрать API для Python/SQL/ETL/аналитического проекта;
- найти источник данных для экономического, финансового, географического, погодного, транспортного, статистического или другого анализа;
- определить, существует ли публичный API для нужного типа данных.

Не используй skill, если пользователь уже явно указал конкретный API или официальный источник и задача заключается только в его использовании. Не используй его для справки по библиотеке или фреймворку, для общего веб-исследования темы и для фактчека уже написанного текста.

Если пользователь сразу просит «найди API для X», не задавай лишних уточняющих вопросов, когда из запроса уже достаточно информации для поиска. Если пользователь просит «получи данные X», найди API и определи конкретный endpoint и параметры запроса по официальной документации.

## 1. Определи, какие данные нужны

Из запроса извлеки только то, что в нём есть:

- тип данных;
- необходимую детализацию;
- географию;
- временной диапазон;
- необходимую частоту обновления;
- формат данных;
- требования к историческим данным;
- требования к бесплатности;
- необходимость API key;
- ограничения по rate limits;
- предполагаемый язык/стек использования, если он известен.

Не додумывай отсутствующие требования. Если они критичны для выбора API, сначала сформулируй их как критерии поиска и ищи с этими критериями. Не блокируй поиск вопросами, если искать уже можно.

## 2. Проверь каталог Public APIs

Репозиторий: https://github.com/public-apis/public-apis

Первый источник кандидатов — README этого репозитория, не агрегаторы и не поисковая выдача.

Как искать:

1. Возьми сырой README: `https://raw.githubusercontent.com/public-apis/public-apis/master/README.md`.
2. Рабочий каталог начинается с `## Index`. Блок выше (промо APILayer, MCP Servers) — не рейтинг релевантности. Не предпочитай API только потому, что оно стоит в промо-блоке.
3. Категория — заголовок `### ...` и таблица `API | Description | Auth | HTTPS | CORS`.
4. Ищи по типу данных, синонимам и связанным категориям, не только по точному названию. Прочитай живой Index в README: набор категорий меняется.
5. Если README слишком большой, ищи внутри него по якорю категории и ключевым словам. Не останавливайся на первой строке.
6. Поля `Auth`, `HTTPS`, `CORS` — непроверенные метки каталога. `No` в Auth не означает отсутствие лимитов и не доказывает бесплатность.
7. Ссылка в колонке API может вести на сайт, docs или чужую страницу. Открой её и найди официальную документацию.

Ориентиры по связанным категориям (сверяй с живым Index):

- stock prices → Finance / Cryptocurrency / Currency Exchange
- macroeconomic data → Finance / Government
- weather → Weather
- country information → Government / Geocoding
- company information → Business / Finance
- population → Government
- maps/location → Geocoding
- scientific data → Science & Math
- datasets for ML → Machine Learning

Если прямого совпадения нет, ищи API, которые могут предоставить нужные данные косвенно.

`https://api.publicapis.org` и другие зеркала не используй как каталог. Источник каталога — GitHub README.

## 3. Сформируй shortlist

Не выбирай первый найденный API. Собери несколько потенциально подходящих вариантов и сравни их по:

1. соответствию требуемым данным;
2. доступности исторических данных;
3. необходимости регистрации;
4. необходимости API key;
5. бесплатному тарифу;
6. rate limits;
7. HTTPS;
8. формату ответа;
9. качеству и полноте данных;
10. актуальности API;
11. наличию официальной документации;
12. пригодности для автоматизированного использования.

Не используй собственную систему баллов или искусственный рейтинг. Если варианты отличаются, опиши конкретные trade-offs.

Пункты 2–12 по возможности бери из официальной документации. Из каталога до проверки docs можно взять только название, описание, ссылку и метки Auth/HTTPS/CORS — и пометить их как каталог.

## 4. Проверь официальный источник

Информация из `public-apis/public-apis` является каталогом, а не гарантией актуальности API.

После нахождения кандидата:

- открой официальный сайт API;
- найди официальную документацию;
- проверь endpoint;
- проверь authentication;
- проверь параметры запроса;
- проверь response format;
- проверь ограничения;
- проверь текущий статус API;
- проверь, действительно ли нужные данные доступны.

Не считай API бесплатным только потому, что оно находится в `public-apis`.

Приоритет источников:

1. Official API documentation
2. Official API website
3. `public-apis/public-apis`
4. Другие надежные источники

Не используй агрегаторы как основной источник, если существует официальная документация.

## 5. Если API требует ключ

Не пытайся получить, угадать или сгенерировать API key.

Укажи:

- что нужен API key;
- где его получить;
- есть ли бесплатный тариф;
- какие ограничения у бесплатного тарифа, если они известны.

Никогда не вставляй секреты или API keys в код, в примеры, в URL и в параметры. Placeholder: `YOUR_API_KEY`.

Если ключа нет у пользователя, остановись на рабочем примере запроса. Не вызывай endpoint, который без ключа вернёт ошибку авторизации, как будто данные получены.

## 6. Если подходящего API нет

Не выдумывай API.

Сообщи, что в каталоге подходящего варианта не найдено, и предложи следующие варианты:

- официальный государственный источник;
- официальный dataset;
- другой публичный API;
- web search для поиска специализированного источника;
- scraping только как последний вариант, если это допустимо.

Если для поиска подходящего источника требуется более широкий web search, явно укажи, что каталог Public APIs не дал подходящего результата. Не подменяй каталог произвольным списком API из памяти, не проверив официальный источник.

## Формат результата

Кратко перечисли критерии, которые реально следуют из запроса.

Если кандидатов несколько, сначала сравнительная таблица:

| API | Данные | Auth | Free tier | Historical | Rate limit | Формат | Основное ограничение |
|---|---|---|---|---|---|---|---|

После таблицы объясни, какой вариант соответствует каким требованиям. Например:

- для полностью бесплатного использования подходит X;
- для исторических данных подходит Y;
- для минимальной настройки подходит Z.

### Найденные API

Для каждого наиболее подходящего кандидата:

- Название
- Что предоставляет
- Почему подходит
- Authentication
- Бесплатность / тариф
- Historical data
- Rate limits
- Формат ответа
- Official documentation
- Ограничения / риски

У фактов, которые ещё не подтверждены docs, пиши «каталог, не проверено». Не заполняй пропуски догадками: если rate limit или история в документации не найдены, так и напиши.

### Рекомендация по использованию

Объясни, какой вариант лучше соответствует конкретным требованиям пользователя и почему, без искусственного рейтинга.

Если пользователь собирается использовать API в коде, дополнительно покажи минимальный рабочий пример запроса. Endpoint, параметры и способ передачи ключа бери из официальной документации, проверенной в этом запуске.

```python
import requests

response = requests.get(
    "https://example.com/api/...",
    params={
        "key": "YOUR_API_KEY",
    },
    timeout=30,
)

response.raise_for_status()
data = response.json()
```

Никогда не вставляй реальный секрет в пример. Используй placeholders вроде `YOUR_API_KEY`.

Если ключ не нужен, не добавляй фиктивный параметр `key`. Покажи тот запрос, который описан в документации.

## Контекст программирования

Найденный API может использоваться внутри Python scripts, Jupyter notebooks, pandas pipelines, SQL/ETL workflows, data analysis, эконометрических исследований, ML pipelines, backend applications.

Если пользователь не указал стек, не добавляй сложную инфраструктуру. Достаточно показать HTTP request и, при необходимости, Python-пример.

`CORS: No` в каталоге мешает вызову из браузера. Для Python, ETL и серверного кода это обычно не ограничение. Не отбрасывай API только из-за CORS, если стек не браузерный.

## Надежность данных

Для аналитических и экономических задач проверь по официальной документации, а не по факту наличия API:

- источник данных;
- периодичность обновления;
- историческое покрытие;
- единицы измерения;
- валюту;
- timezone;
- seasonality/adjustment, если применимо;
- revisions данных, если применимо;
- наличие missing values;
- ограничения бесплатного API.

Не делай вывод о качестве данных только на основании наличия API. Если документация это не сообщает, напиши, что покрытие не подтверждено.
